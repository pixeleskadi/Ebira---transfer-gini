# Automated candidate evidence

Local implementation checks completed with .NET SDK 8.0.426/runtime 8.0.32, JDK 17.0.20.1, Gradle 8.9, Android Gradle Plugin 8.7.3, platform/build-tools 35.

- Native Windows self-contained x64 app: compiled/published with zero compiler warnings/errors.
- Windows offline candidate 4 fixes the approval UI: approval and session ending use checked devices, matching recipient selection. Eight regression assertions passed using the actual form's checked/selected row state and synthetic engine metadata, including checked-without-selection approval, immediate visible state refresh, repeated approval, mixed pending/approved devices, correct session ending, empty checks and expired sessions. Layout/discovery checks pass after the fix. Android offline candidate 3 is unchanged and compatible.
- User-provided screenshot confirms that the original Windows candidate starts and reaches the local-host listening state. It also revealed clipped controls and WARP selected ahead of physical adapters; candidate 2 corrects the layout and adapter ordering. This is startup evidence, not proof of a completed native TLS transfer.
- Offline candidate 3 layout/network checks passed at five window/font combinations (100–200% font sizes), including the screenshot's requested width/height; the local test desktop may cap the actual window height. Controls wrap, page-level horizontal scrolling is absent, and the footer remains reachable through vertical scrolling. WARP/virtual adapter ranking and local IPv4 filtering are checked. Discovery protocol validation and an actual UDP round trip through an active Windows private IPv4 adapter also passed. This is not an Android-to-Windows radio test. Real monitor/DPI changes remain part of device validation.
- Native Android development APK: final build assembled; lint reported no issues. APK signing was verified with apksigner; it uses a development certificate, not a public-release owner key.
- Engine + actual API: **50 checks passed**. The API used the internal loopback HTTP test helper because this Windows sandbox cannot initialize its user cryptographic key profile or Schannel credentials. Native TLS checks are explicitly skipped in that mode.
- Exact Android Api.java transport on a JVM: **18 checks passed** against the real engine through an independent OpenSSL TLS bridge, including rejection of the wrong certificate pin, acceptance of the exact pin, verified reuse of the same TLS connection across consumed requests, multi-chunk transfers in both directions, full-file byte equality, resume offsets, tampered-chunk hash rejection and session revocation.
- Android offline protocol/routing on a JVM: **18 checks passed**, covering discovery nonce/source matching, malformed/public/non-HTTPS origins, certificate pins, display suffix and subnet matching. These use the compiled production classes but do not execute Android OS services. Hotspot creation/permissions, UI and AP-owner local routing still require a physical device.
- Gradle wrapper distribution SHA-256 is pinned. Generated keys, credentials, SDKs, build caches and runtime output are excluded from source control.

The engine/API checks cover pending approval, wrong codes, foreign sessions, 60 GB+1 rejection, checksum mismatch, offset conflicts, source changes, zero-byte/collision behavior, durable offset rollback, recovery after receive-file rename, per-file scheduling, pause/resume/cancel, cleanup, absolute session expiry, rate limits and revocation. Synthetic payloads span multiple 8 MiB chunks; these are not 60 GB transfer tests. IDs are normalized to prevent Windows case-insensitive path collisions from truncating an existing partial.

The GitHub workflow is configured locally to run native Schannel HTTPS checks on a normal Windows runner and build/lint Android. **CI was not run:** the connected GitHub integration rejected creating the source blob with HTTP 403, "Resource not accessible by integration". No branch, commit, PR or release was published. The complete source ZIP includes the workflow for a future authorized push. Configuration alone is not a successful CI result.
